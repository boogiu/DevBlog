## 1. 기존 FSM 방식


- 기본적인 FSM 구조 설명
- 상태 전환 조건을 개발자가 직접 간선으로 정의
- 초반에는 상태가 많지 않아 관리 가능했음

---

## 2. HFSM과 LayeredFSM으로의 전환

- 상태가 늘어나면서 FSM 단독으로는 한계가 왔음
- HFSM: 상태를 계층으로 묶어 상위 상태가 하위 상태를 포함하는 방식
- LayeredFSM: 이동 레이어, 전투 레이어처럼 레이어별로 FSM을 분리

---

## 3. 그래도 남아있던 한계

계층과 레이어로 나눠도 여전히 불편한 게 있었다.

- 상태마다 "이 상태가 끝나면 어디로 돌아가는가"를 직접 지정해줘야 했다
- 예를 들어 공격 중 피격이 발생하면, 피격 종료 후 공격으로 돌아가는 경로를 명시적으로 연결해야 했다
- 새로운 상태가 추가될 때마다 기존 상태들과의 전환 조건을 다시 검토해야 했다
- 결국 조건문과 상태 체크가 계속 늘어나는 구조

---

## 4. 자료구조의 특성을 활용해보기

문제를 다시 보니 두 가지였다.

하나는 **상태 복원** 문제다. 어떤 상태가 끝났을 때 어디로 돌아가야 하는지를 상태마다 지정해주고 있었다.

다른 하나는 **상태 선정** 문제다. 지금 어떤 상태가 실행되어야 하는지를 개발자가 직접 간선으로 연결해주고 있었다.

이 두 문제를 각각 **스택**과 **우선순위 큐**로 접근해보면 어떨까 생각했다.

---

## 5. 스택으로 상태 복원 관리하기

### 기본 아이디어

상태 전환이 발생할 때 이전 상태를 스택에 보존해두고, 현재 상태가 끝나면 Pop해서 자동으로 이전 상태로 복귀하는 방식이다.

```
// 기존 방식
공격 중 피격 발생 → 피격 종료 → IDLE → 다시 공격? 
// 피격이 끝나면 어디로 가야 하는지를 직접 지정해줘야 했음

// 스택 방식
공격 중 피격 발생 → 스택에 [공격] 보존 → 피격 종료 → Pop → 공격으로 자동 복귀
```

## 6. 우선순위 큐로 상태 선정 자동화하기


### 기본 아이디어

입력이나 이벤트가 발생하면 상태 전환 요청을 큐에 Push하고, 큐에서 가장 높은 우선순위의 요청을 꺼내 현재 상태와 비교해 전환 여부를 결정하는 방식이다.

기존에는 개발자가 "A 상태에서 B 입력이 들어오면 C 상태로 간다"는 간선을 직접 연결해줬다. 우선순위 큐 방식에서는 그 결정을 가중치 데이터에 위임한다.
